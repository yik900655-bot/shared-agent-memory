# 工具站立项与交付验证方法

依据用户于 2026-11-11 确认的哥飞 Agent 复盘三层定义整理。固定的是验证方法。模板数量、模型、API、文生图或图生图、图片增强等具体选择，由各项目按用户任务、交付质量、成本和可维护性决定。[Roblox 项目复盘](../03_PROJECTS/roblox-game-icon-generator/retrospective.md)

## 第一层 · 成功定义

开发前先写清四件事。用户是谁？在哪个场景使用？最终要获得什么结果？什么样的结果才算成功？

用一句话写明某类用户在某个场景完成什么任务并拿到什么结果。为交付物写出最低可用质量和可复查的通过标准。技术可运行属于能力证据，用户能拿到并使用符合预期的结果属于产品交付证据。

## 第二层 · 交付路径

亲自以普通用户身份完成核心流程。按实际页面记录进入 → 输入 → 选择 → 配置 → 执行 → 结果 → 修改 → 下载或导出。保存可核查的输入、操作、耗时及输出样本。遇到付费、登录或尚未开放的环节，记录止步位置和原因，把未体验步骤保留为待验证。

体验时回答四个问题。

1. 它让我填什么？
2. 我在哪一步等待？
3. 我在哪一步感到惊喜？
4. 我在哪一步差点放弃？

同时查看价格页，记录价格日期、实际付费节点、限制条件和核心卖点。用能追溯的用户评价、社区讨论或反馈识别真实抱怨，保留原始上下文，区分实际观察、产品方陈述和自己的推断。

## 第三层 · 结果验收

用有权使用的真实输入完成真实任务，打开最终交付物，按成功定义逐项检查。用相同或可比任务与竞品同类结果对照，并由人判断结果质量、使用难度和能否直接使用。上线前人工走完整流程，包括等待、异常提示、必要的修改及下载或导出。

API 返回 200、构建成功和模拟测试通过分别证明了各自的技术环节。产品验收要保留真实任务、实际交付物和人工结论。未走通的步骤或缺失的竞品对照应在记录中标明。

## 九步执行

| 步骤 | 动作 | 完成标准 |
| --- | --- | --- |
| 1 | 一句话定义用户需求 | 能指出目标用户、真实使用场景、任务与最终结果。 |
| 2 | 完整体验竞品 | 至少选择一个与用户任务匹配的竞品，记录普通用户从进入到导出的操作、卡点与实际结果。受阻步骤标为待验证。 |
| 3 | 定义成功标准 | 写出真实输入样例、最低可用质量和人可判断的通过标准。 |
| 4 | 研究核心卖点和付费理由 | 记录产品方怎么承诺、用户在哪一步会遇到付费及真实反馈。价格与用户数据写明来源和时间。 |
| 5 | 用自己的技术栈低成本预检 | 先完成一次代表性的真实任务，记录样本、版本、耗时、成本和能力边界。 |
| 6 | 只做核心 MVP | 列出交付这项结果所需的最少功能和暂缓项。 |
| 7 | 设定投入和停止条件 | 记录开发时间、费用上限、观察期限和继续或暂停的触发条件。开发与试验按授权范围推进。 |
| 8 | 上线前人工走查 | 代表用户能完成核心操作并取得合格交付物，有可追溯的验收记录。 |
| 9 | 上线后按真实数据决策 | 核对实际搜索展示、点击、使用、下载或导出等数据，依预设标准决定继续、调整或暂停。数据缺失时记录原因。 |

调研可直接使用 [调研模板](../templates/research-template.md)。阶段结束按 [试错与持续迭代原则](core-principles.md) 记录产品结果和学习成果。

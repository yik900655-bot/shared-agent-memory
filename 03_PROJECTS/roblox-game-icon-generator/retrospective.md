# 从做出来到真正交付：Roblox 项目复盘

复盘日期 2026-11-11。**产品尚未取得预期结果，这次过程形成了有效的学习成果。** 用户已确认继续采用最小 MVP 市场验证的方向。

## 最初目标和实际进展

最初想给 Roblox 游戏创作者做一个接近成熟竞品的图标工具。用户上传游戏截图、填写描述、选择风格，生成 2～3 个可比较的方案，再预览、下载 PNG。目标交付是一张能用于游戏展示、缩小后主体仍可辨认的图标。

**已核实。** Photobooth 原版已本地运行，产品副本接通了 KIE.ai 并通过模拟测试。浏览器和模拟服务已验证任务查询、防重复提交、预览及 512×512 PNG 下载。用户第一次真实提交时页面报 401，之后同一 Key 通过只读鉴权检查。具体出错环节仍待定位，真实 KIE 成品和完整用户交付尚未验收。[原版验收](local-validation-report.md) · [KIE 接入报告](kie-api-integration-report.md) · [MVP 审查](mvp-scope-and-work-plan.md)

## 这次调研漏了什么

**已核实。** 早期调研记录了竞品公开页面的输入、规格、价格与卖点，也提出了自己的操作流程假设。保存的资料缺少普通用户从进入、填内容、选择和等待，到检查结果、修改并下载成品的完整实操证据。实际在哪一步遇到付费、放弃或觉得结果有价值，也缺少连续记录。历史来源为《Roblox-Website-Research-v1.1》第 6 节及第 7.5 节，选型记录见 [底座调研](research.md)。

**经验。** 复盘中发现，开发验收较早聚焦 API 接通和文件能否下载，容易把技术进展当成交付成功。用户真正需要的是一张愿意拿去用的图标。下一次应先写清产品成功的定义，再用真实任务验证交付路径和结果。

## 图像质量和技术边界

**观察。** 竞品公开页面把真实游戏还原、成品在小尺寸下的清晰度、多个构图方向及快速导出作为价值点。现有验收可证明本地界面、任务流转和 PNG 文件规格，尚无可用于同题对照的真实生成样本。用户实际需要看的差距包括游戏主体还原、构图与光影、150 px 辨识度，以及生成后还需修改多少。差距大小待同输入对照和人工判断。

**推断。** 若要接近成熟工具的表现，可能需要额外的模板、提示词、素材处理和多轮调试。现有证据不足以确认竞品内部实现或精确投入天数。继续增加开发工时，也无法提前证明能获得搜索流量或用户使用。

## 心理调整和范围决定

> 我们不是失败了，只是还没有做成功。

遇到能力边界后，已完成的原型、技术验证和选型工作仍然有价值。它们帮助确认了下一轮必须先验证真实交付，识别出当前缺的能力，并使缩小范围成为有依据的决定。是否继续由接下来的成本和证据决定。完整原则见 [试错与持续迭代](../../01_PRINCIPLES/core-principles.md)。

**用户确认的决定。** 先交付英文最小 MVP，让用户填写名称和描述，生成、预览并下载一张图标。多风格、批量生成和复杂图片处理暂缓。先验收一张真实成品，再观察上线后 30 天的收录、搜索展示、点击、生成和下载。出现市场信号再决定投向哪项能力，缺少明显信号就暂停进一步投入。[MVP 范围与工作量](mvp-scope-and-work-plan.md)
